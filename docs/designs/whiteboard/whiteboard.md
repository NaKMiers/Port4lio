# Design: /admin/whiteboard - a personal context canvas that agents can read

Generated by /office-hours on 2026-09-23

Repo: NaKMiers/Port4lio

Mode: Builder

## Problem Statement

The owner wants one private place under `/admin/whiteboard` to write text, draw shapes, connect items, keep to-do lists, and sketch - but the page is not the goal. The goal is a durable store of "everything about me": dreams, goals, futures, ambitions, drafts, failures. That store must be usable as context for AI, so other things can be created from it.

The first AI use is **ask-me-anything about me**: "what did I want in 2025?", "why did project X fail?", "what are my active goals?". The owner wants to reach that context two ways:

- a UI export that is easy to copy into any chat ("Export to AI"), and
- an owner-only agent endpoint so Claude Code and Codex can read it directly - "this is even quicker than copy-paste".

## What Makes This Cool

The picture is how you put things in. The product is what an agent can read back. Every card carries a _meaning_ (dream, goal, failure, draft, note), every arrow is a real, labelled link ("because", "blocks", "learned from"), and the same serializer feeds both the copy button and the MCP server. So when Claude Code starts a session and asks "who is the owner and what are they working toward?", it gets the same clean, cited markdown the owner would have pasted by hand, with no pasting.

## Constraints

- Owner-only. Lives in the `(admin)` route group, inherits `noindex` from `(admin)/layout.tsx` and the `/admin` Disallow in `robots.ts`. Never touches `PUBLIC_PROFILE_FIELDS`.
- This is the most private data in the database. Some items should never reach an agent at all.
- House rules apply: `requireOwner` on every UI handler, `jsonError`, `readJsonBody`, `compileModel` for new models, `SelectField` for dropdowns, `cn()`, hyphens not em dashes, lucide icons, tests in `tests/unit` + `tests/api`.
- Next.js 16 App Router, React 19, Tailwind v3 `pp-*` tokens. Read the relevant `node_modules/next/dist/docs/` guide before writing route handlers.
- `readJsonBody` defaults to 16 KB; ink strokes will exceed that, so the item routes need an explicit, bounded `maxBytes`.

## Premises

Agreed in session (2 and 4 were revised by the owner):

1. **The canvas is how you put things in; the items and links are the product.** Every card, shape, frame, ink stroke and arrow is its own Mongo document. Position is view data on that document, not the data model.
2. **v1 draws:** typed text cards, to-do cards, shapes (rect / ellipse / diamond), frames, labelled arrows, **and freehand ink**. Ink is stored as points; the AI sees it as `[Sketch near: <nearest items>]` - no OCR is pretended.
3. **One infinite canvas.** Frames group areas ("Career 2027", "Health"); meaning classifies items.
4. **Hard delete is allowed.** (Revised from "archive only".) Deleting an item deletes its links.
5. **Agents get in through an MCP endpoint + a markdown export route**, both gated by a revocable owner token generated in `/admin` and stored hashed, separate from the OTP cookie. **Agent access is read-only in v1.**
6. **Never public:** noindex, excluded from sitemap/robots, nothing reachable without the cookie or a token.

## Cross-Model Perspective

Codex (cold read of a session summary):

- **Coolest version:** a "personal context compiler" - every AI answer cites the exact cards, links and frames it used, and AI-proposed ideas appear as _ghost cards_ until accepted. Over time it becomes a navigable autobiography: goals linked to failed attempts, changing beliefs, "what did I believe before I learned X?".
- **Most revealing line:** "this is even quicker than copy-paste." The excitement is not drawing; it is not having to re-explain yourself to Claude/Codex.
- **Library:** React Flow (`@xyflow/react`, MIT) + `perfect-freehand`. Cards are real React nodes, arrows are real edges, matching per-item documents. Build ink as a custom stroke node; React Flow's own freehand example is Pro-only. Excalidraw gets 50% of the drawing feel for free but its elements are drawing primitives, so typed items, per-item persistence and queryable links would mean fighting its model. Use JSON Canvas as an import/export format, not the schema.
- **Build order:** models, canvas, export drawer, token, then a read-only MCP (Codex proposed two tools).

Synthesis: agreed on library and build order. Two changes adopted:

- Codex's form list becomes `text | todo | shape | frame | ink` (the item's **form**), and dream/goal/failure is a separate **meaning** field - a to-do list can be a Goal, an ink sketch can be a Dream.
- The v1 MCP surface is **three tools** (below), not two - `get_overview` is added because "what are my active goals?" should not need a search query. (A full-board `whiteboard://context` resource was planned and then cut in eng review, D15: at up to 1 MB it overflows Claude Code's 25k-token MCP output cap.)

Ghost cards are parked for v2 as the safe shape for agent writes.

### Taxonomy: form vs meaning

- **form** (required) - what the item _is_ on the canvas: `text | todo | shape | frame | ink`.
- **meaning** (optional) - what it _says about you_: `dream | goal | failure | draft | note`. `null` means unclassified. There is no `todo` meaning; a to-do list is a form, and it can carry any meaning (a to-do list that is a Goal).
- **status** - only meaningful when meaning is `dream` or `goal`: `active | someday | done | dropped`. Ignored (stored as `null`) otherwise. A todo-form item's rows carry their own `done` flags; the item has no derived status.

### Data model (`src/models/`, all via `compileModel`)

```
WhiteboardItem
  _id         ObjectId, generated by the CLIENT (see Save pipeline)
  form        'text' | 'todo' | 'shape' | 'frame' | 'ink'
  meaning     'dream' | 'goal' | 'failure' | 'draft' | 'note' | null
  status      'active' | 'someday' | 'done' | 'dropped' | null
  title       string, single line, <= 200 chars
  body        string, plain text, <= 20,000 chars, never rendered as HTML
  todos       [{ id, text (single line, <= 500), done }], <= 100 rows   (form = todo)
  shape       'rect' | 'ellipse' | 'diamond'                   (form = shape)
  ink         { points: [x, y, pressure][], bbox: { minX, minY, maxX, maxY } }, <= 2,000 points  (form = ink)
              bbox is derived by the SERVER from points on every create/PATCH/restore; a client or file value is ignored (D27)
  parentId    ObjectId of a frame | null
  x, y        RELATIVE to the parent frame's top-left when parentId is set, canvas-absolute otherwise
  width, height, z
  tags        string[], <= 20 tags of <= 40 chars
  when        Date | null   (when this was true / happened / was wanted; readers fall back to createdAt)
  targetBy    Date | null   (deadline or "by" date for dreams and goals)
  includeInAi boolean, default true (see Privacy)
  createdAt, updatedAt

WhiteboardLink
  _id         ObjectId, client-generated
  from, to    ObjectId (items), from != to
  label       string <= 80 chars
  fromHandle, toHandle   string | null
  unique index on { from, to, label } - duplicates are rejected, not merged

WhiteboardToken
  name, prefix (first 8 chars of the token, for display)
  hash        sha256 hex of the full token, unique index
  createdAt, lastUsedAt, revokedAt
```

Other indexes: text index on `title`, `body`, `tags`, `todos.text` with **`default_language: 'none'`** (no English stemming or stopwords - content is mixed Vietnamese/English); `{ meaning, status }`; `{ parentId }`; links on `{ from }` and `{ to }`.

**Coordinates.** Stored the way React Flow uses them: a child's `x/y` is relative to its frame, so dragging a frame writes one document. Ink `points` are local to the ink item's own `x/y`. The serializer computes an absolute bounding box as `parent.xy + item.xy` (+ point bounds for ink). This stays simple because **frames are flat** - a frame can't have a `parentId`, so there is only one level.

**Frame membership.** Drop an item so its centre lands inside a frame: it joins (`parentId` set, `x/y` converted to relative). Drag its centre outside: it leaves (converted back to absolute). Frames can't join frames.

### Write validation (server, every POST/PATCH, rejected with `jsonError`)

- `_id` is a valid ObjectId; `form` is fixed at create and can't change.
- `parentId`, if set, must exist and have `form: 'frame'`; a frame can't have a `parentId` (no nesting, therefore no cycles).
- Field lengths and counts as listed above; titles, labels and todo rows must be single-line (newlines rejected); `ink.points` over the cap -> 413.
- Bulk `PATCH /items` is **all-or-nothing**: every entry is validated first, and one bad entry rejects the whole request with 400 naming it. Only then does a single `bulkWrite` run.
- Links: both ends exist, `from != to`, not a duplicate of an existing `{ from, to, label }`.
- Item routes pass an explicit `maxBytes` of 256 KB to `readJsonBody` (ink); every other route keeps the 16 KB default.

### Privacy: one filter, used by every agent-facing read

`src/lib/whiteboard/data.ts` exports `loadAgentVisible(scope)`. It is the **only** way the export drawer, `context.md`, and the MCP tools read data:

0. **Excluded boards (D32)** = boards with `includeInAi: false`. Every agent query is filtered by the visible board ids first, so a hidden board is invisible whatever its cards say about themselves. It is rule 1 one level up, and it exists for the same reason: a whole board is often one context, and hiding it once is more honest than remembering to hide forty cards.
1. Excluded frames = frames with `includeInAi: false`. **Hiding a frame hides everything inside it**, whatever the children's own flag says. That's how you keep a whole "Private" area off-limits.
2. Visible items = `includeInAi: true` AND `parentId` not in the excluded frames.
3. Visible links = links with **both** ends visible.
4. Ink "nearest item" labels are computed only over visible items in the current scope.
5. Counts in `get_overview` run the same filter.
6. `get_item(id)` on a hidden id returns exactly the same not-found as an unknown id.
7. A link to a missing item is ignored. A `parentId` pointing at a missing item is treated as **hidden**, not visible (fail closed - see Delete).
8. **Exclusion is written down when it would otherwise be lost.** Hiding a frame doesn't touch the children's flags. But when a child leaves a hidden frame (dragged out, or un-parented because the frame was deleted), the server sets that child's `includeInAi: false` in the same write. A card never becomes agent-readable just by moving. Making it visible again is always a deliberate toggle.
9. `search_context` never queries the collection directly. It calls `loadAgentVisible({ kind: 'search', ... })`, which puts the visibility conditions (`includeInAi: true`, `parentId` not in the excluded frames and existing) **inside** the same `$text` query, so the index is used and there is still one privacy path.
10. **Agent reads never load ink points (D27).** `loadAgentVisible` projects out `ink.points` and works from `ink.bbox`. `get_overview` counts use `countDocuments` / an aggregate on the same filter, not a load-then-count. For `search_context`, ink "near" labels are computed over all visible items, loaded bbox-only.

**Default for `includeInAi`: `true`, with an escape hatch and a decision rule.** Autosave persists a card seconds after you create it, so a new card outside a hidden frame is agent-readable immediately. That's acceptable in v1 because agents are read-only and only run when you invoke them, and a card created **inside** a hidden frame inherits the exclusion from its first save. Rule: if the Assignment below has you hesitating over 3 or more of the 15 items, flip the default to `false` before building step 1.

**Un-hiding a frame (D24).** Switching a hidden frame back to visible asks first: "N items inside become agent-readable" [Make all readable] / [Keep items private]. "Keep" writes `includeInAi: false` on the children before the frame flips (one request, children first).

**Showing visibility.** The inspector toggle shows the item's _effective_ visibility. For a child of a hidden frame it is disabled, with "Hidden by frame <title>". On the canvas, every effectively hidden item gets a small lucide `EyeOff` badge, so you can see at a glance what agents can't.

### Modules (`src/lib/whiteboard/`)

- `context.ts` - **the one serializer**, pure, unit-tested: `(visibleItems, visibleLinks, scope) -> markdown`.
  - Grouping: `## <Frame title>` per frame (plus `## Unframed`), then `### <Meaning>` groups (plus `### Unclassified`), then one entry per item: `#### <title>` followed by a meta line `id · meaning · status · when · targetBy · tags`. An empty title renders as `#### (untitled <form>)`.
  - Links: each item lists **both** outgoing (`- blocks -> [[Title]] (id)`) and incoming (`- <- led to [[Title]] (id)`). A visible target that falls outside the export scope still gets its title and id, marked `(outside this export)`. Hidden targets never appear.
  - Todo items render as `- [x] text` / `- [ ] text`.
  - Ink: `[Sketch near: A, B, C]`, up to 3 visible in-scope items whose bounding box is within 200 px of the stroke's, nearest first. With none nearby: `[Sketch]`.
  - Escaping: titles, labels and todo rows are single-line, a leading `#` is escaped, and `[[` / `]]` become `[ [` / `] ]`. Bodies are emitted as a `> ` blockquote, one prefix per line, so a `#` in a body can't open a heading. Tags are rendered as inline code.
  - Size: a full export is expected around 100-200 KB at 500 items, capped at 1 MB. Past the cap, items are **picked by priority**, then rendered in the normal grouping: active dreams/goals first, then everything else by `updatedAt` desc, until the budget is spent. A final line then reads `(truncated: N of M items - use search_context)`. Tests check which items survive.
  - Date rule, shared by every path: a from/to range matches `when ?? createdAt`. A `targetFrom/targetTo` range matches `targetBy`. (D22) All dates are calendar days: `when`/`targetBy` are stored as UTC midnight of the picked day. Params are `YYYY-MM-DD` with both ends inclusive. `createdAt` is converted to a day in `Asia/Ho_Chi_Minh` (`WHITEBOARD_TIMEZONE` in `limits.ts`).
- `data.ts` - Mongo reads/writes, including `loadAgentVisible`, and the delete sequence.
- `token.ts` - create (32 random bytes, `wbt_` prefix, shown once), sha256, verify (`findOne({ hash, revokedAt: null })`, so an unknown token and a revoked one give the same answer at the same cost), revoke, touch `lastUsedAt`. The touch is throttled (D29): a conditional `updateOne` that only writes when `lastUsedAt` is null or older than 5 minutes, scheduled with Next's `after()` so it never delays the answer or fails the request. The token panel shows it as approximate ("used ~5 min ago").

### Save pipeline (client)

- **Client-generated ObjectIds.** Every item and link gets its id when drawn. `POST` is an idempotent upsert (`$setOnInsert`), so a retried create is harmless and a link or edit can reference a card before its first save lands.
- A per-item write queue: creates, then edits, in order. A link's `POST` waits until both ends' creates have resolved.
- Debounced `PATCH` per item (~600 ms). After a multi-select drag, one bulk `PATCH /items` carries all the new positions.
- A status pill: Saved / Saving / N unsaved / Failed - retry. **Only network errors and 5xx are retried** (with backoff). A 4xx (400/413 validation) is permanent: the write leaves the queue and the item is marked with the server's message. You can fix it, or discard the change, which also drops the queued writes that depend on it (for example a link to a card whose create was rejected). `beforeunload` warns while anything is pending or failed.
- Concurrency: one owner, **last write wins**, stated and accepted. No conflict detection in v1.

### Manual save (D31, after v1)

- An **Auto-save** switch in the top bar, on by default and remembered per browser (`localStorage`). Turning it off pauses the queue: every rule it has - coalescing, ordering, dependencies, rule 8 - still applies, and nothing is sent.
- **Save** (the button, or Cmd/Ctrl+S in either mode) drains the queue: the debounce is cleared and it runs to empty, retries and dependent writes included, before it goes back to holding. The pill reads "N unsaved" in amber while writes are held - not the Saving spinner, which would claim they were on their way.
- Paused is not offline, although both stop the pump. Offline happened to the owner and resolves itself; paused is what they asked for, so the network coming back does not send anything.
- **Leaving with writes still waiting asks first**, in both directions: `beforeunload` for a reload or a closed tab, and a confirm dialog on every client-side way off the canvas - the top bar's link back to the hub and the switcher's three (another board, a new one, the index) - which a client-side navigation would otherwise take silently. "New board" asks before it creates, so cancelling leaves nothing behind.
- Held writes are on the canvas and nowhere else, so what the server can answer for - the AI export preview, the context a backup file is built from - does not include them. The pill's count is the standing reminder; Save first. The Backup menu says it outright above Download, because that file is the only way back from a hard delete and a silent one-edit-behind copy is the worst kind to have.

### Many boards (D32, after v1)

- `/admin/whiteboard` is the board index (new, rename in place, the per-board agent switch, delete; a new board stays on the index with its name selected, and clicking a card opens it); `/admin/whiteboard/<id>` is a canvas. A switcher in the top bar moves between them, and also renames the board on screen and flips its agent switch. Delete stays on the index only.
- Switching is a navigation, not a state change: the canvas remounts, so one board's save queue, undo history and held writes can never reach another.
- Every item and link carries `boardId`, and every index leads with it. The text index stays global, because agent search crosses boards.
- **One migration, once:** the first read that finds no board creates "Whiteboard" and adopts every item and link written before boards existed. It only ever runs while no board exists, and two first reads at once both keep the oldest board and drop the other, so the adoption always has exactly one target.
- **Agents read every board whose switch is on**, and an export with more than one board gives each a `##` section, pushing frames to `###`. A single board renders exactly as it always did, so nothing changed for an agent reading one board.
- A board delete is the one destructive act undo cannot answer for - the history lives in the canvas and dies with it - so it is the one place that still asks first, with the item count in the question.
- **Backup and restore are per board**: the file is the board you are looking at, restored into the board you are looking at. An id in the file that already exists on another board is refused rather than moved.

### Share links (D34)

- A board is shared **by link and nothing else**: `share` is `off` (default, and every new board starts there), `view` or `edit`. There is no invite list and no account - the URL is the credential. The owner sets it from the **Share** menu in the canvas top bar, which also renames the link. Every choice in that menu (view or edit, link name, password, time) is a draft until the owner presses **Share** (or **Update** once shared), which sends them as one PATCH. **Unshare** turns the link off. The copy button beside the link copies the saved link only (2026-09-25, owner request).
- The link is `/whiteboard/<slug|id>`. `slug` is optional (lowercase words and single hyphens, 3-64 characters, never 24 hex so it cannot be mistaken for an id) and unique across boards through a partial unique index. Renaming it retires the old name; the id form keeps working, so a link handed out before a rename still opens.
- **The id link is a known, accepted trade-off.** It cannot be rotated (only turning sharing off revokes it), a slug does not hide it (the shared canvas talks to the API by id, so a rename cannot break an open tab), and a Mongo id is a timestamp plus a per-process random value and a counter, so ids made close together by one server run are guessable from each other. For a personal site that is acceptable, and the read rate limit (checked before the lookup) bounds anyone walking through keys. A random, resettable share key is the upgrade if that ever changes.
- The shared page is the owner's canvas component with different chrome: no board switcher, hub link, backup, export or vocab editing, and Share is a plain "Copy link". A view link is the canvas's existing `readOnly` held on for good - no tool rail, no inspector column - with a "View only" chip where the save pill was.
- The API behind it is `/api/whiteboard/shared/<slug|id>/*`, running **the same handler functions** as the owner routes (`canvas-routes.ts`) behind a different gate (`share.ts`): `off` or unknown is a 404 (a link that was turned off does not confirm the board exists), a write on a view link is a 403, edit-link writes are rate-limited per IP (300/min), shared reads - the page itself, the board stream and the vocab list - share their own looser per-IP bucket (120/min, checked before the lookup; over it the page renders a plain "slow down" page), and a share link cannot grow a board past `SHARED_BOARD_MAX_ITEMS` (1,000 items; a 409, the owner is never capped). The board is looked up on every request, so turning a link down or off stops an open tab's next write. A write that already passed the gate when the switch flips still lands a few milliseconds later: closing that needs a transaction, which the repo does not use, and it is accepted.
- **A visitor cannot flip what agents read on existing cards.** A shared PATCH drops `includeInAi` (alone, it is a 403), and the inspector hides the switches. Rule 8 still runs server-side for everyone, so a move out of a hidden frame through a share link still makes the card private. **Creates are not restricted, by the owner's choice:** a card a visitor adds follows the normal default and may be agent-readable - including one re-created under the id of a hidden card they deleted. The share menu warns when an edit link is on a board agents can read, and hiding the board from AI is the way to keep visitors' text away from agents.
- The shared canvas loads the whole board, hidden-from-AI cards included - "Include in AI" is about agents, not people - and draws them like any other card: no dimming, EyeOff badges or hatched frames (Canvas `aiStyling`), because that state is the owner's business and means nothing to a visitor. The vocab list comes without the cross-board usage counts, through a read that never seeds the list (`peekVocab`), so an anonymous visitor never causes a write.
- Concurrency is still **last write wins**, now between people rather than one owner's tabs: there is no live sync, so two editors see each other's changes on reload.
- **An optional password on the link (2026-09-25, owner request).** Off by default, and a board with none behaves exactly as above.
  - **Setting it.** The owner turns it on with the Share menu's **Require a password** switch (Share or Update is refused until a password is typed, so a lock never goes out without one), changes it by editing the field, and removes it by switching it off. With the switch on the field can never be empty. The field exists only with the switch on and is read-only until focused, because a browser autofilling the owner's saved login into it once locked a link with a password nobody had chosen. The owner also picks how long a visitor stays let in: 10m, 1h, 1d (default), 2d, 7d, 30d or unlimited. It is stored as scrypt with its own salt (`share-password.ts`), which is what checks a visitor's try. Beside the hash sits an AES-256-GCM copy (key derived from `AUTH_SECRET`), because the owner asked to see the password again. `GET /api/admin/whiteboard/boards/<id>/password` (owner only, `no-store`) returns it, and the Share panel fills its field with it on open, with an eye button to show it. The board list only carries `passwordSet`. A password is re-sent only if it changed, since re-sending the same one would still sign everyone out.
  - **Unlocking.** Until a visitor unlocks, `/whiteboard/<key>` renders a password form that names nothing about the board, not even its title in the tab. The right password (`POST /api/whiteboard/shared/<key>/unlock`, 10 tries per IP per 15 minutes, checked before the lookup) sets an httpOnly cookie per board, signed with `AUTH_SECRET` over `{ board, access version, issued at }`.
  - **Every route checks it.** Every shared route checks that cookie, not only the page, because the canvas calls the API directly. Without a valid cookie a route answers 401 `{ locked: true }` and writes nothing.
  - **Changing the password signs everyone out.** Every set, change or removal writes a new random access version, and a cookie is only good for the version it was signed with. So an existing session ends on its next request, however much time it had left. Removing a password and setting one again does not revive old cookies.
  - **The time limit.** It is read from the board at check time, counted from when the visitor typed the password. Shortening it ends sessions already open that are past the new limit, and lengthening it extends them. The cookie's browser lifetime is the 400-day maximum; the server decides when it ends.
  - **Scope.** Changing the time alone is not a password change, so it does not sign anyone out. A turned-off link is still a 404, with or without a password.
- The page is `force-dynamic`, `noindex`, `no-referrer` (the URL must not ride along in a Referer), cannot be framed (`frame-ancestors 'none'` + `X-Frame-Options: DENY` in `next.config.js`, so an edit link cannot be clickjacked), and `robots.ts` disallows `/whiteboard/`.

### Sample data (D33)

"Add sample data" (`mock-data.ts`) drops a frame, ten cards (a dream, goals, a failure, a draft, a to-do, a hidden note, a shape) and five labelled links on the board, as one undo step. It is offered on an empty board and in the Backup menu. The seed is a pure function with no ids and no dates of its own, so `tests/unit` checks its shape - every link end exists, every child fits inside its frame - without a canvas or a database.

### Undo/redo (D30, after v1)

- **Cmd/Ctrl+Z** undoes, **Shift+Cmd/Ctrl+Z** and **Ctrl+Y** redo. Inside a field the chord is left to the field, where it undoes the characters just typed.
- Every local edit passes through one function (`useBoard.commit`), which records the board as it was before it. Undo diffs that snapshot against the board and sends the difference through the same save queue as any other edit - there is no second write path. The diff is pure and tested alone (`history.ts`, `tests/unit/whiteboard-history.test.ts`).
- Keystrokes in one field coalesce into one step (700 ms), 60 steps are kept, and a board load or a restore clears the stack: it describes a board that no longer exists.
- **A card brought back by undo is a copy under a new `_id`.** R3-6 makes a deleted id dead for the session, which is what stops a retrying create from resurrecting it; undo does not get an exception, because reviving the id would be a POST racing its own DELETE. The copy carries every field, `includeInAi` included (rule 8 holds: a card that was hidden comes back hidden), and the links it took with it. The rest of the undo stack is rewritten to the new id.

### Delete (hard, premise 4)

- The server deletes in a safe order, with no transaction (the repo doesn't use them, and `mongodb-memory-server` runs standalone): (1) links touching the item, (2) un-parent the children of a frame (convert their `x/y` to absolute, and for a **hidden** frame set `includeInAi: false` on each in the same update), (3) the item. If it stops partway, links to missing items are ignored and a `parentId` pointing at a missing frame reads as hidden, so nothing becomes visible by accident. The confirm for a hidden frame says "its N items stay private".
- The canvas disables React Flow's default Backspace/Delete removal. The Delete key, and the inspector's "Delete", remove the selection at once and leave a toast that says what went ("2 items and 1 link deleted", plus "its 3 items stay on the board, and stay private" for a hidden frame) and carries **Undo**. There is no confirm dialog: since undo/redo shipped (D30), a confirm in front of an undoable action is a click that protects nothing, and the one it used to protect against - a mis-aimed Delete - is now Cmd/Ctrl+Z.
- The **eraser removes ink strokes only.**
- **Backup and restore (D20):** "Download backup (JSON)" and "Restore from backup" (preview counts, then confirm) on the page. This is the recovery path for hard delete.

## Reviewer Concerns

### R3-1 — completeness

**Problem**

> Privacy rule 8 has the server set includeInAi: false when a child leaves a hidden frame, but nothing says the client learns about that write. The client's copy still holds includeInAi: true, so the inspector toggle and the EyeOff badge ('Showing visibility') show the item as visible when it is hidden. Worse, the document never says PATCH /items/[id] sends only changed fields. If a later inspector edit (title, tags) sends the client's full item, it writes includeInAi: true back and the item becomes agent-readable without any deliberate toggle, which breaks rule 8's promise.

**Remedy**

> Have the client apply rule 8 locally when the move happens, and have the server return the resulting document so the client can merge it. State that PATCH sends only the fields that changed, and that includeInAi is sent only by an explicit toggle. Add a tests/api case: drag a child out of a hidden frame, then send an unrelated edit, and the item is still hidden.

### R3-2 — completeness

**Problem**

> Rule 8 and the step-2 test cover 'a child dragged out of a hidden frame', but a multi-select drag sends one bulk PATCH /items carrying parentId for up to 500 entries. The document does not say the bulk path applies rule 8. That requires reading each entry's current parentId and the excluded frames before the bulkWrite. Dragging several private cards out of a hidden frame together is exactly the case where one missed path exposes many items at once.

**Remedy**

> State that bulk PATCH /items loads the current parentIds and the excluded frames, and adds includeInAi: false to every entry that leaves a hidden frame inside the same bulkWrite. Add a tests/api case for a bulk move out of a hidden frame.

### R3-3 — feasibility

**Problem**

> Write validation requires that parentId exists and is a frame. The save queue only makes links wait for their ends' creates. A card drawn inside a frame that was just drawn, or dropped into it, can reach the server before the frame's own create lands. That write gets a 400, and under the save pipeline's rule a 4xx is permanent and leaves the queue, so an ordinary fast gesture turns into a rejected card.

**Remedy**

> Make any item create or PATCH, bulk included, that sets parentId wait until that frame's create has resolved, the same way links wait for both ends. Add a test, or a note in the queue design, for a child created in an unsaved frame.

### R3-4 — consistency

**Problem**

> The save pipeline says every link gets a client id and that a retried create is harmless. Write validation, however, rejects a link that duplicates an existing { from, to, label }. A link POST whose first attempt succeeded but whose response was lost, then retried, would match its own saved document and come back as a permanent 400, so the client would mark a saved link as failed.

**Remedy**

> Make link POST an idempotent upsert by _id ($setOnInsert). Check duplicates only against links with a different _id, and return success for a replay of the same id. Add a tests/api case for a retried link create.

### R3-5 — completeness

**Problem**

> Labelled links are central to the product ('because', 'blocks', 'learned from'), but the routes are only POST /links and DELETE /links/[id]. In React Flow an edge is normally drawn first and labelled afterwards, and labels get corrected. No route or flow sets or edits a label after creation, and the unique { from, to, label } index means an edit also needs its own conflict handling.

**Remedy**

> Add PATCH /api/admin/whiteboard/links/[id] with { label }, the <= 80-char single-line check, and duplicate rejection, sent through the save queue. Or state that the label is chosen when the link is created and that changing it means delete and recreate.

### R3-6 — completeness

**Problem**

> The document does not say how a hard delete interacts with the per-item write queue. A create still being retried with backoff, or a debounced PATCH, can run after the DELETE. Because POST is a $setOnInsert upsert, a late create would bring the deleted item back. A late PATCH would hit a missing document, and its status code and the queue's response are not defined.

**Remedy**

> State that DELETE goes into the item's own queue after its create, that pending edits and dependent link writes for that item are dropped, and that a PATCH to a missing item returns 404 and is discarded, not retried. Test that a deleted item is not recreated.

### R3-7 — consistency

**Problem**

> Delete says the Delete key opens the same confirm dialog as 'Delete permanently', and also that deleting a lone edge needs no confirm. When only an edge is selected and the owner presses Delete, the two statements disagree.

**Remedy**

> State that a selection of edges only is deleted without a confirm, and that any selection containing an item opens the confirm with the item and link counts.

### R3-8 — clarity

**Problem**

> The connect command puts the token in a shell-profile env var 'not typed inline'. But --header "Authorization: Bearer $PORT4LIO_WB_TOKEN" is double-quoted, so the shell expands it when the command runs, and claude mcp add --scope user stores the plaintext token in ~/.claude.json. The env var keeps the token out of shell history, not out of config, so the panel text as implied misstates where the secret lives.

**Remedy**

> Say plainly that the token ends up in the user-level Claude config (private, not committed). Or, if Claude Code's ${VAR} expansion is confirmed for user-scope headers, use the single-quoted literal form. Add that check to the Open Questions next to the Codex config keys.

### R3-9 — feasibility

**Problem**

> search_context can return 25 full item entries, and get_overview up to 20 active dreams/goals plus 10 recent items. Bodies are allowed up to 20,000 chars each, so one tool response can reach hundreds of KB. Claude Code warns about and caps MCP tool output well below that (a default token limit), so the answer would be truncated or refused in exactly the 'what are my active goals?' success path. Only the full export has a size budget.

**Remedy**

> Give each tool response a size budget. Clip bodies in search_context and get_overview results to a fixed length with a '(truncated - get_item <id>)' marker, keep full bodies for get_item, and add a test that a response over the budget is clipped.

### R3-10 — clarity

**Problem**

> The 1 MB truncation drops visible, in-scope items, but the link rules only define markers for hidden targets (never shown) and visible out-of-scope targets ('(outside this export)'). A link to an item that was in scope but dropped by truncation has no defined rendering, so the serializer tests cannot assert it.

**Remedy**

> State how a link to a truncated item renders, for example with its title, id and '(truncated)', and cover it in the step-1 truncation test.

### R3-11 — clarity

**Problem**

> The date rule is 'shared by every path' (when ?? createdAt), but the serializer's meta line lists 'when' without saying what it prints when when is null. If it prints nothing, a pasted export gives an agent no date for that item, while search_context would still date it by createdAt, so the two paths answer 'what did I want in 2025?' differently.

**Remedy**

> State that the meta line shows the effective date (when ?? createdAt, perhaps marked as created) whenever when is null, and add that case to the step-1 date-rule tests.

### R3-12 — clarity

**Problem**

> from/to/targetFrom/targetTo have no defined format, bound inclusivity or timezone, and the document does not say how when/targetBy dates are stored. An agent passing to = 2025-12-31 could miss items dated that day, and a date entered in UTC+7 can land on the previous UTC day. **Remedy**

**Problem**

> search_context allows an empty query 'when filters are given', but the document does not say what happens when both the query and every filter are empty. It could error, list the most recent items, or dump everything up to the limit.

**Remedy**

**Remedy**

### R3-15 — completeness

**Problem**

> Bulk PATCH /items is all-or-nothing and names the bad entry. The client's 4xx rule, however, is written per item ('the item is marked with the server's message'). **Remedy**

**Remedy**

**Remedy**

**Remedy**

> Have the context response include an excluded count, and have the drawer show '<N> selected items are hidden and not included' (or 'This frame is hidden') above the preview.

### R3-19 — clarity

**Problem**

**Remedy**

### Responsive and accessibility (Pass 6: 3 -> 9)

- **DR8** - three tiers:
  - `>= 1024px` (lg): the approved layout.
  - `768-1023px` (md): every tool, pen included (pointer events, so an Apple Pencil draws). The inspector and export become a bottom sheet over the canvas, max 60dvh. Rail buttons are 44px.
  - `< 768px`: view + edit only. Pan and pinch-zoom work, tapping a card opens the inspector bottom sheet, and the rail is replaced by "Drawing needs a larger screen". The frame drops `lg:h-[100dvh]` and fills the viewport minus the safe areas.
  - Touch targets are at least 44px at every tier below lg.
  - _Revised 2026-09-25 (owner request):_
    - `< 768px`: every tool is on a horizontal rail along the top. The rail folds away behind one button, and Undo/Redo stay outside the folding part. Tapping a card opens the inspector over the whole canvas (header to bottom edge), with a close button. The md sheet gets the close button too.
    - Undo/Redo buttons are on the rail below lg and for any coarse pointer, because a phone or tablet may have no Cmd/Ctrl+Z.
    - The top bar is one 48px row at every width. Below md, auto-save, Share, Backup and the hidden chip move into a "More" menu, and the save pill shrinks to its dot.
    - Zoom moves to bottom-right and gains a board lock. It is per-tab view state: while it is on, the board only pans and zooms. Nothing selects, moves, resizes, links or edits (undo included), and no inspector opens. Locking clears the selection.
    - The top-bar buttons are 36px, below the 44px target above, to fit the one row.
- **DR9** - keyboard and a11y:
  - A shortcut guard: tool keys, Delete and `?` do nothing while focus is in an input, textarea or contenteditable.
  - Esc order: exit the tool, then close the sheet/popover, then clear the selection.
  - Cmd/Ctrl+E opens Export. `?` opens the shortcut list.
  - Tab order: top bar, rail, canvas, inspector. On the canvas, React Flow node focus: Tab between nodes, Enter edits, arrows move 10px, Shift+arrow 50px (saved via the debounced PATCH).
  - Rail and icon buttons: `aria-label` with the shortcut ("Text card, T"), and `aria-pressed` on the active tool.
  - The save pill is `aria-live="polite"`. A card error is announced once.
  - Focus ring: 2px `pp-ink-blue`, 2px offset.
  - Hidden state is never shown by colour alone (`EyeOff` + "Hidden from AI" text / aria-label).
  - `prefers-reduced-motion`: no hover lift, no sheet slide, instant fit.
  - Dialogs trap focus. Sheets focus their heading.

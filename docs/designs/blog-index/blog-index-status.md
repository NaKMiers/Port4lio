# Design: Google index status for the blog board

Generated by /office-hours on 2026-10-06

Repo: NaKMiers/Port4lio
Status: APPROVED
Mode: Builder

## Problem Statement

The owner's blog posts don't show up in Google search. Search Console is verified, and the
Page indexing report shows posts as not indexed. The owner wants to see, per post on
`/admin/blog`, whether Google has indexed it. They also want to re-check a post on demand
and resubmit the sitemap. The goal is career and personal brand: people searching the
owner's name or topics should land on these posts.

## What Makes This Cool

- One glance at the board answers "which of my posts can someone find on Google, and why
  aren't the others there". It shows Google's own reason, such as "Crawled - currently not
  indexed", "Duplicate, Google chose different canonical" or "Blocked by robots.txt", not
  just a yes/no.
- **The honest expectation:** this feature makes indexing **visible**. It does not make it
  faster.
  - Resubmitting the sitemap on publish only prompts Google to re-read a feed it already
    knows, which `robots.txt` points to anyway. It carries no indexing guarantee.
  - Judge the feature by "I can see what Google thinks", not by how fast posts get
    indexed.

## Constraints

- **Google offers no API to request indexing for blog posts.**
  - The Indexing API "can only be used to crawl pages with either `JobPosting` or
    `BroadcastEvent` embedded in a `VideoObject`", and abuse "may result in access being
    revoked" ([quickstart](https://developers.google.com/search/apis/indexing-api/v3/quickstart)).
    It is out of scope.
  - The "Request indexing" button in Search Console exists only in the web UI.
  - The sitemap ping endpoint (`google.com/ping`) was retired in 2023.
- **URL Inspection API** (`POST searchconsole.googleapis.com/v1/urlInspection/index:inspect`):
  - It is read-only: it reports status and never triggers indexing.
  - Limits are 2,000 calls a day and 600 a minute per property, shared by every account
    that inspects that property.
  - Scope is `webmasters.readonly`.
  - Its data can lag Search Console's live test by hours to days.
  - It rejects an `inspectionUrl` that falls outside the property.
- **Sitemaps API** (`PUT .../webmasters/v3/sites/{siteUrl}/sitemaps/{feedpath}`):
  - It needs the `webmasters` scope, and the caller must be a Full user or owner.
  - A 2xx response records a submission. When Google next reads the sitemap ("Last read")
    is up to Google.
- **Owner's choices for this design:**
  - No cron for checks. Checks run only when the owner clicks.
  - The cron's auto-publish **does** trigger a sitemap resubmit, because it is a publish
    like any other (see the hook below).
  - Whether the cron should auto-publish at all is out of scope.
  - The owner states the cron's posts are reviewed or based on real events. The code does
    not enforce that: `/api/cron/blog` publishes any post that clears `publishBlockers`.
- **House rules that apply:**
  - Every new route starts with `requireOwner`.
  - Errors go through `jsonError`.
  - Secrets are never in `NEXT_PUBLIC_*`.
  - New models use `compileModel`.
  - One service per write.
  - Bookkeeping writes use `timestamps: false` (R9).
  - Add no dependency that a few lines of `node:crypto` can replace.

## Premises

1. Automation can **check** index status and **resubmit the sitemap**. It cannot force
   indexing. (Agreed.)
2. On a blog whose first post is from 2026-09-19, "not indexed" is mostly Google taking its
   time. Per-post visibility, with the reason, comes first. (Agreed.)
3. Checks are manual (a per-row button and "Check all"). Resubmitting the sitemap on publish
   is fine because it is a side effect of a publish. (Owner's spec.)
4. Discovery is already in good shape: `src/app/sitemap.ts` lists every published post with
   an honest `contentUpdatedAt` lastmod, `src/app/robots.ts` leaves `/blog` crawlable and
   points to the sitemap, canonicals come from `postUrl(origin, slug)` in
   `src/lib/blog/seo.ts`, and `revalidatePublishedPost` refreshes `/sitemap.xml` on every
   write. This feature adds visibility on top and changes none of that.

## Approaches Considered

- **A: check on demand, store nothing.** Rejected: the status disappears on reload, so the
  board can't show every post at a glance.
- **B: store the status on each post.** Chosen. See below.
- **C: B plus IndexNow (Bing/Yandex) and a `get_index_status` MCP tool.** Deferred. It can
  be layered onto B's service later without rework.

## Recommended Approach (B)

```
  /admin/blog row ──[Re-check]──▶ POST /api/admin/blog/[id]/index-status
  board header ──[Check all]──▶ same route, called once per published post,
                                one at a time from the client
  board header ──[Resubmit sitemap]──▶ POST /api/admin/blog/sitemap-submit
  patchPost: status ≠ published ──▶ published ──▶ $unset indexStatus (same write) + scheduleSitemapResubmit()
  illustrate-run (cron publish write) ──────────▶ $unset indexStatus (same write) + scheduleSitemapResubmit()

  routes + hooks ──▶ src/lib/blog/index-status-service.ts   (one service)
                        inspectPost(id)       load published post → inspect → conditional write of Post.indexStatus
                        resubmitSitemap()     submit → write SearchConsoleState
                        (scheduleSitemapResubmit lives in src/lib/blog/sitemap-resubmit.ts - eng review R1)
                        getIndexingConfig()   { configured, problem } from env + origin, never throws, no secrets out
                            ▼
                     src/lib/search-console.ts
                        parseServiceAccount(env)   base64 → JSON → { client_email, private_key }
                        getAccessToken()           RS256 JWT (node:crypto createSign + base64url.ts),
                                                   scope https://www.googleapis.com/auth/webmasters (covers inspect AND sitemap submit)
                                                   → oauth2.googleapis.com/token, one token cached until ~60s before expiry
                        inspectUrl(url) · submitSitemap(feedUrl)
                        every fetch: AbortSignal.timeout(15s), cache: 'no-store'
                            ▼
                     Google Search Console API
```

### URLs and the property

- Both URLs use the **same origin the canonical uses**, `resolveSiteOrigin()`:
  - the inspected URL is `postUrl(origin, slug)`
  - the sitemap is `${origin}/sitemap.xml`
- `GSC_SITE_URL` is the exact property id:
  - `sc-domain:example.com` (domain property), or
  - `https://example.com/` (URL-prefix property).
- `getIndexingConfig()` checks that the origin is covered:
  - Domain property: the hostname equals the domain or ends with `.domain`.
  - URL-prefix property: `${origin}/` starts with the prefix.
  - On a mismatch it returns `problem: 'origin <x> is not inside property <y>'`. This catches
    www vs non-www and preview domains before Google returns a confusing 403.
- `getIndexingConfig()` **never throws**. `resolveSiteOrigin()` throws in production when
  `NEXT_PUBLIC_SITE_URL` is missing or invalid; that throw is caught and reported as
  `problem`, so the board GET can't 500 because of this feature.
- **Semantics:** `configured` is true only when both env vars are present, the key parses,
  and the origin is inside the property. Otherwise `configured` is false and `problem` names
  the cause: absent env, malformed key, origin mismatch, or the origin itself failing.
- Locally, `resolveSiteOrigin()` returns `http://localhost:3000`, which is never inside the
  property. Local checks need `NEXT_PUBLIC_SITE_URL` set to the property's origin; the setup
  steps say so.

### Data: `Post.indexStatus`

An optional sub-document with `{ _id: false }` and `default: undefined`, the same pattern as
`illustration`.

| field                      | source                                 | shown where                                                                           |
| -------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------- |
| `verdict`                  | `indexStatusResult.verdict`            | badge state (mapping below)                                                           |
| `coverageState`            | `indexStatusResult.coverageState`      | badge label for not-indexed states, and tooltip                                       |
| `indexingState`            | `indexStatusResult.indexingState`      | tooltip warning line if ≠ `INDEXING_ALLOWED`                                          |
| `robotsTxtState`           | `indexStatusResult.robotsTxtState`     | tooltip warning line if ≠ `ALLOWED`                                                   |
| `pageFetchState`           | `indexStatusResult.pageFetchState`     | tooltip warning line if ≠ `SUCCESSFUL`                                                |
| `lastCrawlTime`            | `indexStatusResult.lastCrawlTime`      | tooltip "Google last crawled ..."                                                     |
| `googleCanonical`          | `indexStatusResult.googleCanonical`    | tooltip warning line "Google chose <url>" if ≠ ours                                   |
| `userCanonical`            | `indexStatusResult.userCanonical`      | compared with the above                                                               |
| `inspectionResultLink`     | `inspectionResultLink`                 | the badge links here; Search Console's manual Request indexing button is on that page |
| `checkedAt`                | server clock at a successful check     | tooltip "checked ..."                                                                 |
| `lastError`, `lastErrorAt` | error message (max 500 chars) and time | error marker and tooltip                                                              |

**How it is written:**

- **Write contract.** Every check write is
  `PostModel.updateOne({ _id, status: 'published' }, { $set / $unset on indexStatus.* paths only }, { timestamps: false })`.
  - It never touches `updatedAt` or `contentUpdatedAt`. Without that, a check would 409 the
    open editor (R9), break `illustrate-run`'s updatedAt fence, and reshuffle the board,
    which sorts by `updatedAt`.
  - The `status: 'published'` filter closes the in-flight race: if the post is archived or
    deleted during the up-to-15s Google call, `matchedCount` is 0, nothing is written, and
    the route answers 409 `not_published`.
- A **successful check** writes every result field explicitly, using `null` for any field
  the response omits (Google leaves out `lastCrawlTime`, the canonicals and others when they
  don't apply). No value from a previous check survives. It also sets `checkedAt` and
  `$unset`s `lastError` and `lastErrorAt`.
- A **failed check** sets only `lastError` and `lastErrorAt`, so a quota blip doesn't wipe a
  known "Indexed".
- **Lifecycle, on entry.** Every transition _into_ `published` (patchPost and the cron's
  publish write in illustrate-run) `$unset`s `indexStatus` in the same write that sets the
  status. A re-published post therefore always starts as "Not checked", whichever way it
  left: archive through patchPost, or `softDeletePost`, which bypasses patchPost.

### Data: sitemap submit record

- New tiny model `SearchConsoleState` (`compileModel`), with one document at the fixed
  `_id: 'sitemap'`:
  `{ lastSubmittedAt, lastError, lastErrorAt, lastTrigger: 'manual' | 'publish' }`.
- It is written with an upsert on the fixed `_id`. Catch error 11000 and retry once (see
  learning `lazy-upsert-index-race`).
- A successful submit sets `lastSubmittedAt` and `lastTrigger`, and `$unset`s `lastError`
  and `lastErrorAt`.
- A failed submit with code `auth`, `forbidden`, `quota` or `upstream` sets `lastError`,
  `lastErrorAt` and `lastTrigger`, and keeps `lastSubmittedAt`.
- Config failures (`unconfigured`, `bad_config`) write nothing. The board's Not configured
  state already says so.
- Both the header button and the publish hook write it, so a hook that keeps failing (a
  rotated key, a Restricted user) shows on the board rather than only in the Vercel logs.

### Board data

- `listBoardPosts()` adds `indexStatus` to its `.select(...)`, and the client `BoardPost`
  type gains the field.
- `GET /api/admin/blog` adds
  `indexing: { configured: boolean, problem: string | null, sitemap: SearchConsoleState | null }`.
  - `configured` and `problem` come from `getIndexingConfig()`, which is env and origin only,
    does no DB read, never throws, and never sends a secret.
  - `sitemap` comes from a separate `SearchConsoleState` read in the service. A failed read
    degrades to `sitemap: null` and is logged, the same way `listBoardPosts` treats a
    metrics failure, so it never fails the board.

### Badge mapping (published rows only; drafts, archived and deleted show nothing)

Lives in the import-free `src/lib/blog/index-status-badge.ts` (`badgeFor()`,
`shortCoverageLabel()`, the `IndexStatus` type), shared by the board and the server, like
`image-placeholders.ts` (eng review R2).

Evaluated top to bottom; the first match wins:

| condition                                                     | badge                                                                         | colour               |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------- |
| `indexing.configured` is false                                | Not configured (tooltip: `problem`)                                           | muted                |
| no `indexStatus.checkedAt` and no `lastError`                 | Not checked                                                                   | muted                |
| no `checkedAt`, `lastError` set                               | Check failed (tooltip: `lastError`)                                           | rose                 |
| `verdict` = `PASS`                                            | Indexed                                                                       | green                |
| `verdict` = `PARTIAL`                                         | Indexed, warnings                                                             | green with amber dot |
| `verdict` = `FAIL`                                            | short `coverageState` (e.g. "Blocked by robots.txt")                          | rose                 |
| `verdict` = `NEUTRAL` or `VERDICT_UNSPECIFIED`                | short `coverageState` (e.g. "Crawled - not indexed", "URL unknown to Google") | amber                |
| anything else (`checkedAt` set, verdict null or unrecognised) | Unknown result (tooltip links `inspectionResultLink`)                         | muted                |

- **Short labels.** `shortCoverageLabel()` looks up the known `coverageState` strings,
  e.g. "Crawled - currently not indexed" → "Crawled - not indexed" and "URL is unknown to
  Google" → "Unknown to Google". An unseen or reworded string falls back to the raw text cut
  to 28 characters with an ellipsis. The full text is always in the tooltip.
- If a result exists _and_ `lastErrorAt` > `checkedAt`, the result badge stays and gets a
  small rose dot. Its tooltip says "last re-check failed: <lastError>".
- When `configured` is false, Re-check, Check all and Resubmit sitemap are disabled, and
  their tooltip is `problem`.
- The tooltip always includes "checked <relative>" and "crawled <relative>", plus any warning
  lines from the table above.

### Board UI (`BlogBoard.tsx`, `PostRowActions.tsx`)

- **Re-check:** one more `RowAction` (lucide `SearchCheck`, tone `blue`) on published rows.
  It updates that row in place from the route's payload (below), not with a full `load()`.
  That includes after a failure, because the error payload carries the `indexStatus` that was
  just written.
- **Header:**
  - "Check all" shows `n/N` progress, where N is the number of published posts when it
    starts.
  - "Resubmit sitemap" shows "submitted <relative>" from `indexing.sitemap`. It shows a rose
    marker with `lastError` when `lastError` is set, which only happens while the most
    recent attempt failed, since success clears it.
- **Mutual exclusion:** while Check all runs, every Re-check is disabled. While any row
  check runs, Check all is disabled.
- Check all's loop is the pure `runCheckAll(ids, checkOne, onProgress)` in
  `src/components/blog-admin/check-all.ts`; BlogBoard only wires it to the buttons (eng
  review R4).

### Route payloads

- `POST /api/admin/blog/[id]/index-status`:
  - 200 returns `{ indexStatus }`, the sub-document as just written.
  - 429 and 502 return the `jsonError` body plus `code` plus `indexStatus` (with the fresh
    `lastError`/`lastErrorAt`, and any prior result kept).
  - 404, 409 and 503 return `jsonError` plus `code` only, since nothing was written.
- `POST /api/admin/blog/sitemap-submit`:
  - 200 returns `{ sitemap }`, the `SearchConsoleState` as just written.
  - 429 and 502 return `jsonError` plus `code` plus `sitemap`.
  - 503 returns `jsonError` plus `code` only.
- The board replaces the row's `indexStatus`, or the header's `indexing.sitemap`, with the
  payload. It never builds that state on the client.

### Errors and statuses (route responses, `jsonError` plus a `code`)

The rows marked _(index-status only)_ can't occur on sitemap-submit, which takes no post id.
Every other row applies to both routes. In "effect", `lastError` means
`Post.indexStatus.lastError` on the index-status route and `SearchConsoleState.lastError` on
sitemap-submit (rules in their sections above).

| situation                                                                                       | status | code            | effect                                                             |
| ----------------------------------------------------------------------------------------------- | ------ | --------------- | ------------------------------------------------------------------ |
| _(index-status only)_ id not a valid ObjectId, or no such post                                  | 404    | `not_found`     | nothing written, no Google call                                    |
| _(index-status only)_ post not `published` (checked before the call, and by the write filter)   | 409    | `not_published` | nothing written                                                    |
| env var absent                                                                                  | 503    | `unconfigured`  | nothing written                                                    |
| key not base64 / not JSON / missing `client_email` or `private_key`, or origin outside property | 503    | `bad_config`    | nothing written; the message names the env var and the fix         |
| token endpoint rejects the JWT (`invalid_grant`, bad key)                                       | 502    | `auth`          | `lastError`                                                        |
| Google 403 (account not on the property)                                                        | 502    | `forbidden`     | `lastError`: "add <client_email> as a Full user on <GSC_SITE_URL>" |
| Google 429                                                                                      | 429    | `quota`         | `lastError`                                                        |
| other Google 4xx/5xx, timeout, network                                                          | 502    | `upstream`      | `lastError`                                                        |

- The config checks are explicit presence and shape checks done before any network call, so
  a missing or broken key gives a 503, not a 500. The routes don't use `getRequiredEnv` here
  for that reason.
- **Check all** stops at the first `unconfigured`, `bad_config`, `auth`, `forbidden` or
  `quota`, because those will repeat on every row, and says why. It continues past
  `upstream`, `not_found` and `not_published` (a row archived in another tab or by the cron)
  and ends with "N checked, M failed".

### Publish hook

- `scheduleSitemapResubmit()` lives in its own thin module `src/lib/blog/sitemap-resubmit.ts`,
  mirroring `revalidate.ts`, so tests mock it whole (eng review R1). It is called from
  exactly two places:
  1. **Inside `patchPost`, after the successful write**, only when the previous status was not
     `published` and the new one is. This covers the board's Publish button, the editor,
     MCP `publish_post` (which goes through `patchPost`) and archived to published.
  2. **In illustrate-run's cron publish loop**, which bypasses `patchPost`. That write
     filters on `_id` and `updatedAt`, not on status, and it still matches when the owner
     published the post while the run was drawing. So both the `$unset` of `indexStatus` and
     the hook apply **only when `fresh.status !== 'published'`**: the `$unset` is added to the
     update conditionally, and the hook call is gated on the same flag. It is called once,
     only after `written.matchedCount > 0` (where `published = true` is set) and before the
     `break`. Never before the matchedCount check, because that write is optimistic and
     retries.
- It is **not** inside `revalidatePublishedPost`. That function runs on every edit and
  forbids swallowing errors; this one must swallow and log.
- **Config gate first:** it calls `getIndexingConfig()`. When `configured` is false, it
  returns without a network call or a write. A site that never set up Search Console stays
  silent, and a broken key already shows as Not configured on the board, with `problem`
  naming the cause.
- Mechanism:
  - It calls `after(() => resubmitSitemap('publish'))`, wrapped in try/catch, which only
    logs.
  - If `after()` throws (called outside a request scope) or the platform cuts the callback
    at the end of the cron's 300s budget, the resubmit is simply lost. That is acceptable:
    Google still finds the sitemap through `robots.txt`, the next publish resubmits, and the
    header button shows the stale "submitted" time.
  - There is no awaited fallback, so a publish never waits on Google.

### One-time setup (owner)

1. Google Cloud: create a project, enable the **Google Search Console API**, create a service
   account, and download its JSON key.
2. Search Console: Settings, then Users and permissions, then add the service account's email
   as a **Full** user. Restricted is not enough for sitemap submit.
3. Set `GSC_SERVICE_ACCOUNT_JSON` (the key, base64) and `GSC_SITE_URL` in Vercel and
   `.env.local`. Add both to `.env.example` with these steps in the comment.
4. For local checks, also set `NEXT_PUBLIC_SITE_URL` in `.env.local` to the property's
   origin (for example `https://example.com`). Otherwise the origin is `localhost` and the
   board shows Not configured, "origin outside property".

## Success Criteria

### R3-1 — feasibility

**Problem**

> The design treats illustrate-run's publish write as a 'transition into published' that `$unset`s indexStatus and calls scheduleSitemapResubmit. But that write (illustrate-run.ts, the `PostModel.updateOne({ _id: postId, updatedAt: fresh.updatedAt }, { $set: { status: 'published', ... } })` in the publish loop) filters on `_id` and `updatedAt` only, not on status. The run itself handles the case 'The post was published while this run was drawing'. If the owner published the post mid-run, `fresh.status` is already 'published', yet the write still matches. As specified, it would then wipe a valid indexStatus and schedule a resubmit for something that isn't a transition. That contradicts the patchPost rule ('only when the previous status was not published').

**Remedy**

> State that, in illustrate-run, the `$unset` and scheduleSitemapResubmit apply only when `fresh.status !== 'published'`: either add the `$unset` conditionally and gate the hook call on it, or add `status: { $ne: 'published' }` to the filter and handle the miss. Add an api test: post already published before the run's publish write, then indexStatus is kept and there is no resubmit.

### R3-2 — consistency

**Problem**

> Next Steps item 4 still says 'The publish hook in patchPost and illustrate-run, and the archive `$unset`'. The design moved the lifecycle rule to entry ('Lifecycle, on entry ... `$unset`s `indexStatus` in the same write that sets the status'), and nothing unsets on archive any more. ### R3-4 — completeness

**Problem**

**Remedy**

**Remedy**

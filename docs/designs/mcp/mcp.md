## Problem Statement

Today the only MCP server on the site is `/api/whiteboard/mcp`: three read-only whiteboard tools behind a `wbt_` bearer token. The owner wants their own Claude Code and Codex sessions to run the whole site: write and publish blog posts with generated images, read the profile and CV, read metrics for the blog and the MBTI/IQ products, look after the whiteboard and the CCA-F tracker, and do admin chores. So the MCP moves from the whiteboard to the project level, with one server and one token system for every domain.

Four scenes are the acceptance tests. Each one must work end to end from a Claude Code prompt:

1. **Idea to published post.** "Write a post about what I learned shipping the whiteboard." The agent reads the whiteboard and profile, drafts in the owner's voice, lints the draft, generates a cover and inline images, sets kind and series, saves a draft, and publishes when the token allows it.
2. **Weekly business briefing.** "How did this week go?" The agent reports blog views and shares, top posts, subscriber growth, MBTI/IQ funnel, paid orders, revenue and conversion, each compared with the previous period.
3. **Me as context.** "Load who I am." The agent gets the profile, CV, active goals and recent posts in one call. "Tailor my CV for this job posting."
4. **Site operator.** "Fix the typo in my headline." "Archive posts published over a year ago with no views in the last 180 days." "Log my mock exam score." The agent does admin chores. Blog events keep 180 days, so "no views" can only mean no views in the last 180 days.

Scene acceptance is a **manual, scripted check**. `docs/designs/mcp/acceptance.md` will list the exact prompts (from the Assignment) and the observable result each must produce, and the owner runs them after each phase. Deterministic tool behaviour is covered by `tests/api` and `tests/e2e`. Natural-language prompts are not automated.

## What Makes This Cool

**The agent writes; the site is its hands and its style guide.** Claude Code is already a strong writer. The site should not act as a second author for it. The site lends the owner's voice (`brief.ts`) as an MCP prompt, lints drafts with the owner's own prose audit (`auditProse`), and does what the agent can't: generate images, store them on the one allowed image host, save, publish and revalidate.

**Scopes decide which tools a token can see.** A read-only token's `tools/list` has no `publish_post` at all. Each token then carries a small tool list, which keeps tool choice accurate. A leaked token also can't tell what a stronger token could do.

## Constraints

- Clients are **Claude Code and Codex CLI only**, using a bearer token in a header. OAuth and claude.ai connectors are out of scope for this design.
- House rules apply:
  - `jsonError`, `readJsonBody`, `checkRateLimit`, `compileModel` for new models
  - `getRequiredEnv`
  - `cn()`, `SelectField`, lucide icons, hyphens not em dashes
  - tests in `tests/unit`, `tests/api` and `tests/e2e`
  - a doc comment with an ASCII flow on every module that carries an invariant
- `REQUIRE_ADMIN=false` must never open the agent route. The route goes through its own guard, never `hasOwnerAccess` (see the header of `src/lib/whiteboard/token.ts`).
- Vercel functions: `maxDuration` 300 s and a 4.5 MB body cap. `runGeneration` and `illustratePost` already live inside that budget.
- The blog read path keeps one cache and one invalidation: route ISR plus `revalidatePublishedPost(slug)`, and no `unstable_cache`.
- The whiteboard privacy rule stays where it is: every whiteboard read an agent makes goes through `loadAgentVisible`.
- Next.js 16: read `node_modules/next/dist/docs/` before writing route handlers.

## Premises

Agreed in session. Premise 3 was amended by the owner (token prefix). Premise 5 was revised twice: first by the owner, then after the second opinion.

1. **One server, CLI clients.** A single MCP at `/api/mcp` serves the whole site. Claude Code and Codex connect with bearer tokens.
2. **The MCP is a front door, not a second implementation.** Every tool calls a `src/lib/<domain>` service, and the matching `/api/admin/**` handler calls the same service. Pulling blog, profile, taxonomy and CCA-F write logic out of the route handlers into services is part of the work.
3. **Scoped `p4_` tokens.** They replace `wbt_`. The scopes are `read`, `write`, `publish` and `pii`. Scopes filter `tools/list`, and the server checks them again on every call. Permanent purge is never exposed.
4. **The agent writes.** The site provides:
   - the owner's voice rules, as both the `write-post` prompt and the `get_writing_brief` tool (built from `brief.ts`)
   - `lint_draft` (`auditProse` plus a dry run of the markdown pipeline)
   - images, persistence, publishing and revalidation

   The server-side pipeline (`runGeneration`) is **deferred**: no scene needs it, it would make the server a second author, and it is the only tool that runs close to the 300 s limit.
5. **No customer's personal data leaves the server.** Metrics are aggregates. `find_order` (scope `pii`) looks up one order by its order code and returns that order's status, never the email or the certificate name. Rationale:
   - The MBTI and IQ privacy pages (vi and en) promise "no sharing with third parties" and "That address is used only to send your result".
   - Tool output goes to Anthropic or OpenAI and stays in local transcripts past the 21-day TTL.
   - None of the four scenes needs raw emails.

   Lookup by email is deferred until the privacy pages disclose AI-assisted support lookups. The contact inbox and subscriber lists are out.

   The owner's **own** contact details (in `resume`) are deliberately inside `read`. `/cv` already publishes them, so a `read` token reveals nothing the public page doesn't show.
6. **Intent-shaped tools.** About 25-30 tools in total, not a CRUD mirror of the admin API. Every answer stays within the ~32,000-character budget (whiteboard D18). Every write goes into an audit log shown in `/admin`.
7. **Whiteboard migration.**
   - `/api/whiteboard/mcp` becomes a thin alias for one release, then is deleted.
   - Existing `wbt_` tokens keep **exactly** the access they have today during that release: the alias and `GET /api/whiteboard/context.md`, nothing else. `/api/mcp` refuses `wbt_` tokens, so no existing token quietly gains site-wide access.
   - Token management, including listing and revoking the legacy tokens, moves from the board's Agents popover to an `/admin/agents` page.
   - Whiteboard writes only ever touch items the agent can already see.

## Approaches Considered

### Approach A: Grow the whiteboard server
Rejected. It creates two write paths for posts. Forgetting `revalidatePublishedPost`, the archived-to-draft 409 or the image-host check in the MCP copy would fail silently.

### Approach B: Service layer + scoped tool registry - CHOSEN
Described below.

### Approach C: Action catalog (about 5 generic tools + `run_action`)
Rejected. `run_action` would have to be `destructiveHint: true` for everything, so the Claude Code and Codex approval prompts could no longer tell "read metrics" from "publish post".

## Recommended Approach

### Request flow

```
  Claude Code / Codex
      │  POST /api/mcp   Authorization: Bearer p4_...
      ▼
  src/app/api/mcp/route.ts           thin: guard, then handler, then sseToJson (as today)
      │
      ├─ guardAgent(request, { accept: ['p4_'] })     src/lib/mcp/token.ts (moved from lib/whiteboard)
      │     1 checkRateLimit(MCP_AGENT_LIMIT, by IP)         guesses count before auth
      │     2 Bearer p4_ ──▶ AgentToken.findOne({hash, revokedAt: null})   401 same for all misses
      │          throws ──▶ 503                              FAIL CLOSED
      │     3 after(): throttled lastUsedAt touch             (D29, unchanged)
      │     ──▶ { tokenId, name, scopes }
      │
      ├─ createMcpHandler(server => registerTools(server, token))   src/lib/mcp/server.ts (C1)
      │     mcp-handler builds a fresh McpServer per request; the closure registers ONLY the
      │     tools and prompts the token's scopes allow (tools/list is filtered)
      │     a tools/call naming a registry tool the token lacks ──▶ isError + refused row (R1)
      │
      ▼
  runTool(def, args, ctx)           src/lib/mcp/run-tool.ts, wraps EVERY tool
      try:
        1 recheck def.scope ∈ ctx.scopes          the filter is not the gate
        2 zod-parse args                          isError teaching message on failure
        3 clientRef claim (R4): insert pending AgentAction under unique (tokenId, clientRef)
            duplicate: ok ──▶ replay · pending ──▶ "still running" · refused/error ──▶ run again
        4 per-token cost bucket (R5): checkRateLimit('mcp-token:<id>', BLOG_GENERATE_IMAGE_LIMIT, ...)
        5 def.run(args, ctx) ──▶ src/lib/<domain> service   (the same one /api/admin/** calls)
        6 budget safety net (C10): list tools page, single objects are capped; a clip that
          still fires appends "[truncated: N chars dropped]" and logs
      finally:
        7 if def.audited (every write tool + find_order): ONE AgentAction row,
          ok | refused(scope|invalid|rate) | error. Keyed calls finalize their claim row
          awaited; unkeyed rows are written via after()

  /api/whiteboard/mcp (alias)  and  GET /api/whiteboard/context.md
      guardAgent(request, { accept: ['p4_', 'wbt_'] })
        wbt_ ──▶ WhiteboardToken ──▶ scopes = ['whiteboard:legacy']   (only these two routes honour it)
        p4_  ──▶ AgentToken, must hold 'read'
```

**How the token reaches a tool (settled, C1).** mcp-handler already constructs a fresh `McpServer` on every request (`node_modules/mcp-handler/dist/index.mjs:195-198`). So the route verifies the token first, then passes an initializer that closes over `{ tokenId, name, scopes }`. The initializer registers only the permitted tools and prompts, and each tool reads the token from the closure. There is no handler cache and no `withMcpAuth`. Tool definitions and their JSON schemas are built once at module load; registration only filters and binds them. The scope recheck in step 1 is still the gate.

### Scopes

| Scope     | Grants                                                                              | Default on new token |
| --------- | ----------------------------------------------------------------------------------- | -------------------- |
| `read`    | every read tool, `lint_draft`, `get_writing_brief`, `context.md`                    | on                   |
| `write`   | drafts, images for unpublished posts, whiteboard writes, CCA-F writes               | on                   |
| `publish` | anything that changes what the public sees: publish, archive, soft delete, any change to a live post (text or images), profile edits (never the `resume`, R8), taxonomy | off |
| `pii`     | `find_order` only                                                                   | off                  |

`whiteboard:legacy` is internal. It is held only by migrated `wbt_` tokens, it is never grantable, and it disappears with the alias.

**The live-post rule.** `update_post`, `generate_image` (attach mode) and `illustrate_post` check `publish` at run time whenever the target post is `published`. Only these tools, plus `publish_post`, `archive_post` and `delete_post`, can change a post's status, and **status is not an input to `update_post`**.

#### Tool behaviour details

- **`create_draft` slug and retries.**
  - If no `slug` is given, it is derived with the existing `slugify(title)` (which folds Vietnamese diacritics and `đ`, and caps at 80 characters), then checked against `SLUG_PATTERN` and `isReservedSlug`, as `validateManualSpec` does (C9).
  - On a clash with any post, soft-deleted ones included, the tool returns an `isError` naming the clash and suggesting `<slug>-2`. It never reuses or overwrites the existing post.
  - Every field is validated and the markdown rendered BEFORE a single insert, so a failure leaves no post behind (C9).
  - Retry safety: see `clientRef` in the request flow (R4). No change to the Post schema for this.
- **Truncated bodies can't be saved (R6).** `get_post` pages the markdown, and `update_post` changes a body with `edits: [{ find, replace }]`. Each `find` must match the current body exactly once, so text the agent never saw cannot vanish. A whole-body replace is allowed only for a post that fits in one page, with its `version`; the 50% shrink guard stays on that path only.
- **`get_briefing` windows follow retention.** Every period is compared with the equal period before it.

  | Section | Source | Periods |
  | --- | --- | --- |
  | Blog views, shares and attributions per post | document counts in `PostEvent.createdAt` (never `$sum: '$count'`) | up to 90 days, because both windows must fit inside 180 days |
  | Subscribers | new confirmations from `Subscriber.confirmedAt`, and unsubscribes | any |
  | Orders and revenue | paid orders from `Payment`/`IqPayment` (`status: 'paid'`, by `paidAt`) | any |
  | Test funnel and conversion (paid divided by paywall-seen) | `TestEvent` | up to 10 days, because both windows must fit inside the 21-day TTL. For a longer period the section is left out with a one-line reason, never computed over expired data |

  `week` is the default and covers every section.

### Where revalidation lives

**Inside the service, never in a front door.** Each mutating service function calls the right invalidation itself, after its write succeeds:

- `revalidatePublishedPost(slug)` whenever the post is published before OR after the change. That covers publish, a live PATCH, archive, soft delete, an image attached to a live post, and a slug change.
- `revalidateTag(PUBLIC_PROFILE_CACHE_TAG, 'max')` after every profile write, the same two-argument call as `src/app/api/profile/route.ts:76`.
- `revalidatePath('/blog')` from `taxonomy-service` after a kind or series change, as the kind PATCH does today (C8).
- `illustratePost` revalidates a live post after its image saves, even with `publish: false` (C8).

`generate-run.ts` is the template only for "no auth, no body parsing inside". Invalidation moves in, because it is exactly the step a second front door would forget. An e2e test under `next start` covers every mutating blog tool, not just `publish_post`, including `illustrate_post` on a live post and `save_taxonomy` refreshing `/blog`.

### MCP prompts

In Claude Code these show up as slash commands, e.g. `/mcp__port4lio__write-post`. Clients that don't surface MCP prompts get the same text from `get_writing_brief`, and the tool descriptions of `create_draft` and `lint_draft` point to it. Whether Codex CLI surfaces MCP prompts is unverified, and this fallback makes the answer irrelevant.

- `write-post(topic, language, kind?)`: assembled from `brief.ts`: `THE_METHOD`, `THE_SHAPE`, `THE_EVIDENCE_LAW`, `SENTENCE_RULES`, `tellsFor(language)`, `markdownContract`, `structureFor`. It ends with the loop: draft, `lint_draft`, fix, `create_draft`, `generate_image`/`illustrate_post` (then poll `get_post` until the illustration is idle), then `publish_post` if `publish_post` is in your tool list. Prompts are registered per request, so their text matches the token (C6).
- `weekly-briefing(period?)`: `get_briefing`, then a short written review. If `whiteboard_add_item` is in your tool list, it also records a dated briefing card on the whiteboard, linked to the goals whose numbers moved.
- `tailor-cv(job_posting)`: `get_me`, then a tailored CV in markdown. It never writes the profile; the resume is edited only in `/admin/settings` (R8).

### Whiteboard writes

- **Visibility.** An agent can only create an item on a board with `includeInAi: true`, at top level or inside a visible frame. The new item gets `includeInAi: true`, so it is visible to `loadAgentVisible` and the agent can read it back and link it. Links need both ends visible, which is today's rule. `whiteboard-export-parity.test.ts` gains a case for an agent-created item.
- **Marking agent cards.** Agent-created items carry the existing `tags` field value `agent`. There is no new schema field, so the backup format, `visible.ts` and the parity test don't change. The card renders its tags as it does today. A dedicated badge is left for the design review.
- **Concurrent edits.** `whiteboard_update_item` requires the item's `updatedAt` from the agent's last read. If the owner changed it since, the tool returns `isError` ("changed since you read it; re-read and retry"), so an agent never overwrites a newer owner edit. The reverse is accepted: an owner's pending save in an open tab wins over an agent edit, because the owner's edit is the most recent.
- **Open tabs.** An open board does not learn about agent-created items live. They appear on the next load. Live refresh is out of scope.

### Data model changes

- **`AgentToken`** (new, `compileModel`), in its own collection:
  - fields: `name`, `prefix`, `hash` (sha256), `scopes: string[]`, `lastUsedAt`, `revokedAt`, `createdAt`
  - token format: `p4_` + 32 random bytes in base64url, shown once
- **`WhiteboardToken`** stays read-only for the alias release:
  - no new `wbt_` tokens can be created
  - `/admin/agents` lists these tokens under "Legacy whiteboard tokens" and can revoke them
  - dropped in phase 5, together with its collection
- **`AgentAction`** (new, `compileModel`), the audit log and the idempotency ledger:
  - fields: `tokenId`, `tokenName`, `tool`, `clientRef?`, `target { kind, id, slug? }`, `outcome` (`ok` | `refused` | `error`), `reason?`, `resultPreview?`, `argsPreview`, `at`, `expireAt`
  - `argsPreview`: at most 2 KB, markdown bodies replaced by their length, never an email
  - `resultPreview`: kept only when `clientRef` is set, for replay
  - rows: exactly one per call to an audited tool (every write tool, plus `find_order`), including refusals
  - TTL index: 180 days, the same window as blog events
  - `outcome` also has `pending` while a keyed call runs; unique partial index on (tokenId, clientRef) (R4)
- **`Post`** gains an `illustration` subdocument: `state`, `leaseUntil`, `remaining`, `lastError` (R2, R3).
- **New indexes (R11):** `PostEvent { kind: 1, createdAt: -1 }`; `Payment` and `IqPayment { status: 1, paidAt: -1 }`. `retention.test.ts` asserts they build.

### Services to extract (premise 2)

Write logic lives inside these handlers today. Each extraction keeps the admin route's behaviour byte for byte, and the route's existing tests must pass unchanged before any tool calls the service. Routes with no tests today (`POST api/profile`, `PUT api/ccaf`, `GET api/admin/metrics`) first get behavior tests written against the current code (R10):

- `src/lib/blog/post-service.ts`
  - extracted from `api/admin/blog` (GET, POST) and `api/admin/blog/[id]` (GET, PATCH, DELETE)
  - adds the `list_posts` query, filters and sorts
  - the admin PATCH still accepts `status`; the MCP simply never passes it
  - revalidation moves inside, as described above
  - the admin PATCH gains an optional `baseUpdatedAt`: when it is stale the answer is 409, and the editor shows a Reload / Overwrite anyway banner. A PATCH without it is unchanged (R9)
- `src/lib/blog/image-service.ts`
  - extracted from `admin/blog/[id]/image-prompt` and `generate-image`
  - `generateImageUrl()` keeps the route's "return, don't save" behaviour
  - `attachImage()` is new: it saves to the cover or a placeholder and revalidates if the post is live
- `src/lib/blog/illustrate-run.ts` gains a `publish: false` option, a per-post lease, patch-in-place image saves and per-token image budgets (R3, R5). The cron keeps its current default and uses the same lease and patch path.
- `src/lib/blog/taxonomy-service.ts`, from the `kinds` and `series` routes.
- `src/lib/profile-service.ts` offers two operations that share validation and revalidation:
  - `replaceProfile(body)`: the admin route's whole-body `$set`, unchanged, so the settings editor keeps its tests
  - `patchProfileSection(section, value, version)`: new, for `update_profile`; refuses `resume` (R8)
- `src/lib/ccaf/progress-service.ts`, from `PUT api/ccaf`.
- `src/lib/metrics/` (new): `briefing.ts`, `tests.ts` (moved from `api/admin/metrics`), `orders.ts`.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — feasibility

**Problem**

> `handlerFor(scopes)` registers ONLY the tools in the token's scopes, so a `read` token calling `publish_post` by name never reaches `runTool`. The MCP server answers with its own unknown-tool error, and steps 1 and 7 never run. The success criterion 'Calling any non-`read` tool by name with that token returns `isError`, writes nothing, and leaves one `refused` AgentAction row' therefore cannot pass as the request flow describes it. Step 1's 'the filter is not the gate' recheck can only fire for tools that are registered.

**Remedy**

> Choose one. (a) Register every tool, filter only the `tools/list` response, and let step 1 refuse and audit. (b) Add a catch-all for unregistered names at the route or handler that writes the `refused` row. (c) Restate the criterion as 'unknown-tool error, no write, no row', and keep `refused` rows for run-time refusals such as the live-post rule. Then test whichever you chose.

### R2-2 — completeness

**Problem**

> Truncated reads can still be saved, which was R1-14's obligation. `get_post` returns a `version` token on every page, so an agent that read only page 1 still holds a current version. The shrink guard only catches a new body under 50% of the old one. For a post of about 24k to 48k characters, a body built from page 1 alone (about 24k) passes both checks and silently cuts the tail. `get_profile` also pages an over-budget section, but `update_profile` replaces a whole section with no version or shrink guard at all.

**Remedy**

> Make a body write require proof of a complete read. For example, return `version` (or a hash of the full body) only with the page that has `complete: true`, or offer an offset/length range replace instead of a whole-body replace. Apply the same rule to `get_profile`/`update_profile` sections, and add an API test with a post just over one page.

### R2-3 — consistency

**Problem**

> `runTool` step 6 says every answer is 'clip[ped] to the response budget', but the Budget success criterion says 'over-budget bodies come back paged, never clipped'. Only `get_post` and `get_profile` have paging. Nothing says what `get_me` does (profile + CV + goals + 5 posts), or what `list_posts`, `whiteboard_search` and `get_briefing` do when they exceed the budget.

**Remedy**

> Say for each tool whether it pages or clips. Paged tools never clip. Tools that clip return an explicit truncation marker and say what was dropped. Then reconcile step 6 with the success criterion.

### R2-4 — completeness

**Problem**

> Step 3 replays any `AgentAction` row with the same (tokenId, clientRef) from the last 24 h, and step 7 writes rows for `refused` and `error` outcomes too. A retry after a rate-limit refusal, a validation error or a transient service error would therefore replay the old failure for 24 h, not try again. That defeats the retry safety that `clientRef` exists to give.

**Remedy**

> State that only an `ok` row is replayed. A `refused` or `error` row does not block a retry with the same `clientRef`. Add an API test for a retry after a refusal.

### R2-5 — feasibility

**Problem**

> The idempotency ledger is written 'via after() so it never blocks the answer', which is after the response and after the service call. A client that times out and retries while the first call is still running, or two calls sent close together, both miss the ledger and both execute. No unique index on (tokenId, clientRef) is defined. `resultPreview` has no size rule, and the design never says whether it holds the full result or only a preview, yet it is what a replay returns.

**Remedy**

> Before step 5, claim the key by inserting a pending row under a unique partial index on (tokenId, clientRef). Finalize that row in `finally`. An in-flight duplicate gets a 'still running' answer, and a replay returns the stored full result, bounded by the budget. Test concurrent duplicates, not only sequential ones.

### R2-6 — clarity

**Problem**

> `clientRef` appears only in `create_draft`'s inputs, but step 3 is written as generic. It is unspecified which other tools accept it. That matters most for the paid tools (`generate_image` in URL mode, `illustrate_post`), which are the likeliest to be retried after a client timeout and the costliest to repeat.

**Remedy**

> List the tools that accept `clientRef`, at least `create_draft` and `generate_image`, and say how a retry of each of the others behaves.

### R2-7 — feasibility

**Problem**

> `illustrate_post` can run for about 255 s. `illustratePost` loads the post once and calls `post.save()` after each image with the body it holds in memory. It has no lock and no version check. Two things can go wrong. (1) An `update_post`, or an owner editor save, that lands during the run is overwritten by the next per-image save, which bypasses the `version` concurrency that `update_post` enforces. (2) A client timeout below 255 s (Open Question 3 is unresolved) followed by a retry starts a second concurrent run on the same placeholders. That doubles the image cost, and the two runs clobber each other's saves.

**Remedy**

> Add a per-post illustration lease so a second run returns 'already running'. Make each per-image save conditional (re-read the post and apply the URL to the current body, or check the version). State this in the illustrate-run changes and cover it with an API test.

### R2-8 — completeness

**Problem**

> The only change listed for `illustrate-run.ts` is the `publish: false` flag. Today that function calls `revalidatePublishedPost` only on the publish branch. With `publish: false` on a live post (allowed for a token with `publish`), each image is saved into the live post, and nothing in the listed change invalidates `/blog/<slug>`. The general 'services revalidate' rule is not applied to this service.

**Remedy**

> State that `illustratePost` revalidates when the post is live, after each save or once at the end, even with `publish: false`. Include `illustrate_post` on a live post in the e2e revalidation test.

### R2-9 — completeness

**Problem**

**Remedy**
